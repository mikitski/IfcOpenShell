# IfcOpenShell Python Core Layer & Low-Level C++/SWIG Binding

Research for IfcOpenShell-TS planning. Scope: the `ifcopenshell` Python package's
core layer (`__init__.py`, `file.py`, `entity_instance.py`, `guid.py`, `settings.py`,
`template.py`, `validate.py`, `stream.py`, `sql.py`, `draw.py`), the low-level
`ifcopenshell_wrapper` SWIG binding it sits on (via its `.pyi` stub and the `.i`
interface files), and the geometry-access API. Excludes `ifcopenshell.api` and
`ifcopenshell.util` (covered elsewhere).

All paths below are absolute, rooted at `/Users/mykytayurtyn/projects/IfcOpenShell`.

**Framing note**: this research was conducted before the project owner fixed v1's low-level binding
target as Node.js/N-API rather than browser/embind (`00-overview.md` §2). The document below still
says "embind" throughout — every design concern it raises (object identity/wrapper-per-access,
exception translation at the binding boundary, the attribute-value tagged-union marshaling contract,
polymorphic class downcasting) applies identically to an N-API binding; only the specific host API
differs. Read "embind" below as "the native binding layer, N-API for v1, embind for the later
browser phase" — see `10-architecture.md` for the resolved decision and `research/04-wasm-js-infra.md`
for the concrete N-API-vs-hand-written assessment.

## 1. Architectural key: `file_mixin` / `entity_instance_mixin`

Before the per-module breakdown, the single most important structural fact:

**The Python-level `file` and `entity_instance` classes are not pure-Python
wrapper classes around an opaque C object — they are produced by multiple
inheritance at SWIG-generation time**, combining a pure-Python mixin with the
SWIG-generated C++ binding class:

- `src/ifcopenshell-python/ifcopenshell/file.py` defines `class file_mixin` — pure Python, no C++ calls except through a handful of primitive methods it expects the C++ side to provide (`create`, `by_id`, `by_guid`, `_by_type`, `_by_type_excl_subtypes`, `_add`, `_remove`, `_traverse`, `_traverse_breadth_first`, `_get_inverse`, `_get_inverse_indices`, `entity_names`, `get_max_id`, `header`, `schema_identifier`, `storage_mode`, `to_string`, `write`/`_write`, `batch`/`unbatch`).
- `src/ifcwrap/IfcParseWrapper.i` line 970: `%feature("python:abc", "file_mixin") ifcopenshell::file;` — this SWIG directive makes the *generated* `ifcopenshell_wrapper.file` class inherit from `ifcopenshell.file.file_mixin`. The `.pyi` stub confirms this at line 846: `class file(file_mixin):`.
- Symmetrically, `entity_instance_mixin` (in `entity_instance.py`) is grafted onto the generated `express::base` → `entity_instance` class the same way (`IfcParseWrapper.i` line 980; `.pyi` line 754: `class entity_instance(entity_instance_mixin):`).
- `ifcopenshell/__init__.py` then does `from .ifcopenshell_wrapper import entity_instance, file` — i.e. the public `ifcopenshell.file` and `ifcopenshell.entity_instance` classes ARE the SWIG classes (with the mixin folded in), not a separate Python wrapper layer.

**Implication for IfcOpenShell-TS:** there is no clean seam where "the C++ binding ends and the Python logic begins" as two separate objects — they're the same object via inheritance. A TS port must decide how to reproduce this: either (a) an embind/WASM class that already implements the low-level primitives, subclassed/extended in TS with a `FileMixin`-equivalent that adds transactions, undo/redo, `by_type()` subtype expansion, `add()`, `write()`, schema-string parsing, etc. — mirroring the split exactly — or (b) a single flattened TS class. Given `file_mixin` and `entity_instance_mixin` contain substantial, non-trivial, engine-independent logic (transactions/undo-redo, `get_info` fallback, attribute proxying, comparison semantics), **(a) is strongly recommended**: port `file_mixin` and `entity_instance_mixin` near-verbatim to TS, and implement only the primitive methods list above in the WASM binding layer.

## 2. Per-module breakdown (core files)

### 2.1 `ifcopenshell/__init__.py` (472 lines)

Purpose: package entry point — loads the native extension, defines `open()`/`Error`/`SchemaError`, schema lookup, format guessing, streaming helpers, RocksDB conversion, and the global `create_entity()` convenience function.

State held:
- `_global_ifc_models: dict[str, file]` — a module-level cache of "default" files keyed by lowercased schema name, used by the free-function `ifcopenshell.create_entity()`.
- `version_core` / `__version__` / `version` — read from the wrapper at import time.

Public surface:
- `open(path, format=None, *, should_stream=False, readonly=False, mmap=False, bypass_types=None, logger=None) -> file | sqlite | stream` — the main entry point. Dispatches on guessed/given format: `.ifcSQLite` → `sql.sqlite`; `should_stream` → `stream.stream`; `.ifcZIP` → unzips to a `tempfile.TemporaryDirectory()` then recurses; otherwise calls into `ifcopenshell_wrapper.open`/`file.create_uninitialized().initialize()`/mmap variants, then checks `f.good()` against `file_open_status` enum (`READ_ERROR`, `NO_HEADER`, `UNSUPPORTED_SCHEMA`, `INVALID_SYNTAX`, `UNKNOWN`) and raises `IOError`/`Error`/`SchemaError` accordingly.
- `register_schema(schema)` / `schema_by_name(schema=None, schema_version=None) -> schema_definition` — schema registry/introspection entry points; `schema_version` tuples are formatted into strings like `IFC4X3_ADD2_TC1` via the `("IFC","X","_ADD","_TC")` prefix convention used throughout the codebase.
- `guess_format(path) -> ".ifc" | ".ifcZIP" | ".ifcXML" | ".ifcJSON" | ".ifcSQLite" | "rocksdb" | None` — extension-based; a directory guesses to `"rocksdb"`.
- `stream2(path, mmap=False, page_size=0)` / `stream2_from_string(data)` — low-level generators over `ifcopenshell_wrapper.instance_streamer`/`stream_from_string`, yielding raw per-instance dicts (id/type/attrs), pull data through Python's `open()`+`f.read(page_size)` when `page_size` is set (page-by-page feeding, browser-File-API-friendly), otherwise hands a path straight to the C++ streamer.
- `convert_path_to_rocksdb(ifcspf_path, rocksdb_path, skip_supertypes=None)` — invokes `ifcopenshell_wrapper.RocksDbSerializer` to build an on-disk (directory-based) key-value store. Desktop-only.
- `create_entity(type, schema="IFC4", *args, **kwargs) -> entity_instance` — module-level convenience creating/reusing a hidden default `file` per schema.
- `set_plugin_search_paths` / `get_plugin_search_paths` / `clear_plugin_search_paths` — path-list passthrough to the native plugin loader (desktop plugin `.so`/`.dll` discovery — not applicable in WASM).
- `get_log()`, `logger`, `logger_or_root()`, `optional_logger_args()` — logging plumbing around `ifcopenshell_wrapper.logger`.

Dependencies: `os`, `sys`, `tempfile`, `zipfile`, `pathlib.Path` — all filesystem-oriented. Nearly everything delegates straight into `ifcopenshell_wrapper`.

Browser/WASM notes: `path.exists()`, `zipfile.ZipFile` + `tempfile.TemporaryDirectory()` for `.ifcZIP`, and the platform-detection block (`os.uname()`, `sys.platform`, appending a native-lib search path) are all Node/desktop-filesystem-shaped and need a browser-native replacement (e.g. take an `ArrayBuffer`/`File`/`Blob` instead of a path, unzip with a JS zip lib, use an in-memory Emscripten FS or in-memory buffer instead of `TemporaryDirectory`).

### 2.2 `ifcopenshell/file.py` (932 lines)

Purpose: defines the pure-Python `file_mixin` base class, the undo/redo `Transaction` system, and a RocksDB lazy-loading storage layer.

Public class/function surface:
- `class Transaction` — records `CreateOperation | EditOperation | DeleteOperation | BatchDeleteOperation` dicts; `serialise_entity_instance`/`serialise_value`/`unserialise_value` walk attribute trees converting `entity_instance` ↔ `{"id": ...}` or `{"type": ..., "value": ...}` dicts for storage; `batch()`/`unbatch()` coalesce inverse-reference bookkeeping for bulk deletes; `rollback()` and `commit()` replay operations by calling back into `self.file` (`create_entity`, `remove`, `by_id`, item assignment). Pure Python, engine-independent — **directly portable to TS**.
- `class UndoSystemError(Exception)`
- `class file_mixin` — the base class grafted onto the native `file` class (see §1). Key members:
  - Class-level shared state trick: `registry: dict[int, list]` maps `id(native pointer)` → `[history, future, transaction]` triple, because SWIG hands out a *new* Python wrapper object on every attribute access, so `self.state` can't simply be an instance attribute — `post_init(iden=None)` (called by the SWIG-side `__setattr__` hook on `this`, see §4) looks up or creates this shared state keyed by the underlying C++ pointer identity (`int(self.this)`). This is the mechanism that makes undo/redo/transactions survive across "different Python identity, same C++ object" — **a WASM/embind port needs an equivalent identity-keyed shared-state registry**, since embind objects have the same "wrapper per access" problem unless explicitly cached.
  - `history`/`future`/`transaction` — properties proxying into `self.state[0]/[1]/[2]`.
  - `set_history_size`, `begin_transaction`, `end_transaction`, `discard_transaction`, `undo`, `redo` — undo/redo stack management (default `history_size = 64`).
  - `create_entity(type, *args, **kwargs) -> entity_instance` — calls native `self.create(type, eid)`, then maps positional/keyword args to attribute indices via `get_argument_index`, sets each via `e[idx] = arg`, records a `Transaction.store_create` if a transaction is active. Also the basis for the `f.createIfcWall(...)`-style dynamic method sugar via `__getattr__` (`attr[0:6] == "create"` → `functools.partial(self.create_entity, attr[6:])`).
  - `schema` (property) / `schema_version` (property) — parse `schema_identifier` string (e.g. `"IFC4X3_ADD2_TC1"`) via the `("IFC","X","_ADD","_TC")` prefix regex convention into `"IFC4X3"` / `(4,3,2,1)` tuples. Pure string logic — portable as-is.
  - `mvd` (property) — returns `MvdInfo(self.header)` from `ifcopenshell.util.mvd_info` (out of scope, but note the dependency at the boundary).
  - `__getitem__` — int → `by_id`, str/bytes → `by_guid`.
  - `add(inst, _id=None)` — calls native `_add`, and if a transaction is active, walks `traverse(result)` to find newly-added entities (`id() > max_id`) and records `store_create` for each in reverse order.
  - `by_type(type, include_subtypes=True)` — dispatches to native `_by_type` or `_by_type_excl_subtypes`.
  - `traverse(inst, max_levels=None, breadth_first=False)` — dispatches to native `_traverse`/`_traverse_breadth_first`.
  - `get_inverse(inst, allow_duplicate=False, with_attribute_indices=False)` — dispatches to native `_get_inverse`/`_get_inverse_indices`, wraps in `set` or `list`/`zip` depending on flags.
  - `remove(inst)` — records `Transaction.store_delete` then calls native `_remove`.
  - `batch()`/`unbatch()` — thin wrappers recording into the transaction, delegate to native `batch`/`unbatch` (note: recursive self-call bug-looking pattern `return self.batch()` — this actually calls the *native* SWIG method of the same name since Python MRO resolves to the C++-side method after the mixin method already ran; relies on the specific inheritance order established by `%feature python:abc`).
  - `__iter__` — iterates `entity_names()` and yields `self[id]`.
  - `assign_header_from(other)` — copies `FILE_DESCRIPTION`/`FILE_NAME` header sub-fields.
  - `write(path, format=None, zipped=False)` — creates parent dirs (`Path.mkdir(parents=True, exist_ok=True)`), guesses format, delegates to native `_write(str(path))`, and if `zipped`, renames + zips via `zipfile.ZipFile`. **Filesystem-bound** — needs a browser replacement returning bytes/Blob instead of writing to a path.
  - `to_string()` — **bug of note**: `def to_string(self): return self.to_string()` is infinite recursion in the mixin as written; in practice this name resolves to the native SWIG `to_string()` method (same MRO trick as `batch`/`unbatch`) — i.e. the mixin doesn't actually override it at runtime, it's just declared for typing/documentation purposes. Worth flagging as a subtlety of the MRO trick rather than replicating literally.
  - `storage` (property) — if `storage_mode() == 1` (RocksDB-backed), returns a `rocksdb_file_storage` wrapper.
- `class rocksdb_lazy_instance` / `class rocksdb_file_storage` — a from-scratch lazy, on-demand deserializer that reads directly from a RocksDB key-value byte layout (`binary_deserializers` tuple: 16 typed decoders keyed by a leading byte, mirroring the C++ `argument_type` enum) without going through the C++ `express::base` layer at all. This is a **desktop/native-only, RocksDB-embedded-database-specific code path** — not relevant to a browser target unless RocksDB is replaced by e.g. IndexedDB with an equivalent binary encoding (unlikely to be prioritized for v1 of IfcOpenShell-TS).

Browser/WASM notes: `write()` uses `pathlib`/`zipfile`; `rocksdb_*` classes assume a native RocksDB C++ extension (`IFOPSH_WITH_ROCKSDB` build flag) with a filesystem-backed directory database — entirely inapplicable to WASM without embedding a WASM-compiled RocksDB or dropping this path.

### 2.3 `ifcopenshell/entity_instance.py` (407 lines)

Purpose: pure-Python `entity_instance_mixin`, grafted onto the native `express::base`/`entity_instance` class (see §1) exactly like `file_mixin`.

Public surface (`entity_instance_mixin`):
- `__getattr__(name)` — the core of IFC's "dynamic schema" illusion. Calls native `get_attribute_category(name)` (0=invalid,1=forward,2=inverse,3=derived — see the C++ `%extend express::base { get_attribute_category }` in §5) to branch:
  - forward → `self.get_argument(self.get_argument_index(name))`
  - inverse → `self._get_inverse(name)`, optionally unpacked to a scalar/`None` if `settings.unpack_non_aggregate_inverses` and the inverse's cardinality bounds are `(-1,-1)` (requires consulting the schema's `inverse_attribute` bound1/bound2 — express-rule-execution mode)
  - neither → falls through to EXPRESS *derived*-attribute calculation: dynamically imports `ifcopenshell.express.rules.<Schema>` (generated Python rule functions, see §4 below) and walks supertypes looking for `calc_<Type>_<name>`. This is the most "codegen-dependent, filesystem-optional" path (falls back to compiling `.exp`→`.py` via `subprocess.run([sys.executable, "-m", "ifcopenshell.express.rule_compiler", ...])` if the schema module isn't importable) — **not relevant to a base TS port**, only to express-rule validation tooling.
- `__setattr__(key, value)` — resolves `get_argument_index(key)`, then `self[index] = value`; raises `AttributeError` if the index sentinel `0xFFFFFFFF` comes back.
- `__getitem__`/`__setitem__(idx, value)` — index-based attribute access; `__setitem__` records `self.file.transaction.store_edit(...)` before calling native `set_attribute_value_py(idx, value)`.
- `__eq__`/`__ne__` — identity-first (`self.identity() == other.identity()`), else same-`is_a`, else falls back to deep value comparison via `get_info(recursive=True)` if `settings.compare_instances_by_value` is set or the instances come from different files or aren't "real" entities (simple/defined types).
- `is_entity()` — `isinstance(self.declaration, ifcopenshell_wrapper.entity)`.
- `compare(other, op, reverse=False)` and the `__lt__`/`__le__`/`__gt__`/`__ge__` partials — EXPRESS-style ordering: entities compare `(type,) + tuple(self)`; simple types compare unwrapped scalar values.
- `__dir__` — merges `get_attribute_names()` + `get_inverse_attribute_names()` for REPL/introspection ergonomics.
- `walk(f, g, value)` (staticmethod) — generic recursive tree-transform helper used throughout the codebase (also directly used by `file.py`'s `Transaction`). Pure Python, portable as-is.
- `get_info_py(include_identifier=True, recursive=False, return_type=dict, ignore=(), scalar_only=False)` — pure-Python fallback implementation of `get_info`.
- `get_info(...)` — performance path: delegates to native `ifcopenshell_wrapper.get_info_cpp(self, recursive, include_identifier)` for the common case (`recursive=True, return_type=dict, ignore=()`), else falls back to `get_info_py`. **This is a case where the C++ layer offers a bulk/recursive serialization fast-path purely for performance** — worth replicating in the WASM binding (a single call that returns a fully-recursive plain JS object) rather than reimplementing the recursive walk attribute-by-attribute in TS, which would cross the JS↔WASM boundary once per attribute per instance.
- `__dict__ = property(get_info)` — makes `vars(instance)` / instance introspection work.

Dependencies: `functools`, `itertools`, `operator`, `importlib`/`subprocess`/`sys`/`time` (only used by the derived-attribute rule-compilation fallback path — not core). No filesystem access in the primary (non-derived-attribute) code paths.

### 2.4 `ifcopenshell/guid.py` (156 lines)

Purpose: GUID codec — IFC's custom base64 alphabet (`digits + uppercase + lowercase + "_$"`, vs. standard `A-Za-z0-9+/`) for compressing/expanding 128-bit UUIDs to/from IFC's 22-character GlobalId strings.

Public surface: `compress(uuid) -> str`, `expand(guid) -> str`, `split(uuid) -> str` (adds dashes), `new() -> str` (generates via `uuid.uuid4()`).

Dependencies: `re`, `string`, `base64.b64decode/b64encode`, `uuid.uuid4`. **100% pure, portable string/byte logic — trivially portable to TS** (JS has no built-in `uuid4`/base64-with-custom-alphabet, but both are simple to reimplement; `crypto.randomUUID()` covers `uuid4`).

### 2.5 `ifcopenshell/settings.py` (57 lines)

Purpose: two module-level boolean flags read by `entity_instance_mixin`: `unpack_non_aggregate_inverses` (default `False`) and `compare_instances_by_value` (default `False`). No classes/functions — just global mutable config, set by user code like `ifcopenshell.settings.compare_instances_by_value = True`. Trivial to port (e.g. as a small exported mutable object/module in TS, or a config object passed to the file/entity APIs).

### 2.6 `ifcopenshell/template.py` (114 lines)

Purpose: generates a minimal valid empty IFC4 SPF file as a string, for `ifcopenshell.file()`-from-scratch bootstrapping.

Public surface: `TEMPLATE` (a `%`-format STEP/SPF text template), `DEFAULTS` (dict of lambdas providing defaults: application string, GUID, schema identifier, MVD name-per-schema, timestamps via `time.strftime`/`time.gmtime`), `get_pep440_version(version_str)`, `create(filename=None, timestring=None, organization=None, creator=None, schema_identifier=None, application_version=None, timestamp=None, application=None, project_globalid=None, project_name=None, mvd=None) -> file`. Ends with `file.from_string(TEMPLATE % d)`.

Dependencies: `time`, `uuid`, `guid.compress`, `ifcopenshell_wrapper.version`. All pure string formatting + the GUID module — **fully portable**, no filesystem access (`from_string` parses an in-memory string, not a path).

### 2.7 `ifcopenshell/validate.py` (893 lines)

Purpose: standalone CLI tool + library (`python -m ifcopenshell.validate ...`) that walks a file's entities and checks attribute values against the schema's declared types (simple/named/enumeration/select/aggregation/type-declaration), reporting violations through a pluggable logger interface, optionally also running compiled EXPRESS derivation/global rules.

Public surface: `ValidationError`, `json_logger` (structured logger with `set_state`/`log`/dynamic level methods, produces a flat list of `{level, message, type, instance, attribute}` statements — good shape for a browser UI to consume), `annotate_inst_attr_pos()` (produces a caret-annotated string pointing at a bad attribute, for terminal/CLI output), `format(val)`, `assert_valid_inverse()`, `get_select_members()`, `assert_valid()` (the core per-attribute type checker — walks `simple_type`/`named_type`/`enumeration_type`/`select_type`/`aggregation_type`/`type_declaration` via `attribute.type_of_attribute()` recursively, matches Python value types against `simple_type_python_mapping`), `log_internal_cpp_errors()` (parses `ifcopenshell_wrapper.get_log()` output and re-emits as logger calls), `get_entity_attributes()`, `validate(f, logger, express_rules=False)` (top-level entry: iterates `f` calling `assert_valid` on every instance, and if `express_rules`, additionally runs `ifcopenshell.express.rule_executor` against generated per-schema rule modules), `validate_guid()`, `validate_ifc_header()`, `validate_ifc_applications()`, `LogDetectionHandler` (a `logging.Handler` that raises `AssertionError`/captures Python exception tracebacks emitted through the schema-declaration's EXPRESS-rule execution machinery — used to bridge Python's `logging` module output into the validator's own statement stream).

Dependencies: heavy use of `ifcopenshell.ifcopenshell_wrapper` schema-introspection classes directly (not routed through `entity_instance`/`file` convenience wrappers) — this file is a good "worked example" of using the low-level `.pyi` schema classes (`named_type`, `simple_type`, `aggregation_type`, `type_declaration`, `enumeration_type`, `entity`, `select_type`, `attribute`, `inverse_attribute`, `schema_definition`) directly. `argparse`, `sys`, `os`, `re`, `json` for the CLI. No inherent filesystem *requirement* for the library functions themselves beyond the CLI entry point reading a path — the `validate(f, ...)` function itself takes an already-open `file` object.

### 2.8 `ifcopenshell/stream.py` (451 lines)

Purpose: an **alternative, non-C++, read-only file backend** (`class stream(file)`) that never fully parses the file into the C++ in-memory graph — instead it does a single-pass line index of an SPF text file (byte offsets per `#id=` line, keyed by `id_map`/`class_map`), and lazily parses individual entity lines on demand using a hand-written `Lark` LALR grammar (`StreamTransformer`). It creates one "shadow" native `ifcopenshell.file(schema=...)` purely so that per-type static schema metadata (`get_attribute_category`, attribute declarations) can be queried via one throwaway instance per IFC class (`shadow_file.create_entity(type)`), without ever building the full graph natively.

Public surface: `class stream(file)` — overrides `create_entity` (raises, not supported), `by_id`, `by_type`, `traverse`, `get_inverse`, and exposes `schema`/`schema_identifier`/`header` properties; `class stream_entity` — read-only, lazily parses its own SPF line via the shared `Lark` parser on first attribute access, `__setattr__` raises; `class stream_wrapper` — per-entity attribute/inverse-attribute cache plumbing.

State held: `id_map` (id→class), `class_map` (class→[ids]), `id_offset` (id→byte offset in file), `inverses` (id→[referencing ids], built by a simple regex `#(\d+)` scan over each line — a coarse, false-positive-tolerant approach, not a real inverse-attribute-typed index), `entity_cache`, `instance_map` (per-class shadow instance cache).

Dependencies: `lark` (external pure-Python parser library — optional import, guarded by `LARK_AVAILABLE`), Python file object opened via `builtins.open(filepath, "r")` kept open for the object's lifetime, seeking (`self.file.seek(offset)`) + `readline()` on every lazy attribute access. **Directly filesystem/streaming-seek-dependent** — the whole design assumes random-access seek on a real file handle. A browser port would need this rewritten against an in-memory buffer / a `Blob`/`File` with `slice()`+`FileReader`, or dropped in favor of always fully loading via WASM `file.open`. Given IFC files intended for web viewing are typically loaded fully into memory (a `File`/`ArrayBuffer`) rather than incrementally streamed from local disk, this module's *design rationale* (memory-conservation for huge files opened by desktop tools) is less relevant in-browser, though the underlying idea (a lazy dict-like proxy) could still be useful for huge-model chunked loading.

### 2.9 `ifcopenshell/sql.py` (548 lines)

Purpose: another alternative backend, `class sqlite(file)`, reading a pre-converted IfcOpenShell-specific SQLite schema (produced by the separate `Ifc2Sql` IfcPatch recipe, not by this module) via Python's stdlib `sqlite3`. Structurally near-identical to `stream.py`'s design: `sqlite_entity`/`sqlite_wrapper` mirror `stream_entity`/`stream_wrapper`, again using a "shadow" native file purely for per-class schema metadata queries.

Public surface: `class sqlite(file)` — `__init__(filepath)` opens `sqlite3.connect`, reads a `metadata` table (asserts `preprocessor == "IfcOpenShell-1.0.0"`), an `id_map` table; `by_id`, `by_type`, `traverse`, `get_inverse` (SQL `SELECT ... WHERE`, with a JSON-encoded `inverses` column per row), `get_geometry(ids) -> GeometryCache` — **notable: this is a fully worked example of a triangulated-mesh (verts/edges/faces/material_ids/materials) query against pre-baked geometry tables**, unpacking via `numpy.frombuffer` on stored binary blobs. `class sqlite_entity` — per-row lazy attribute access via `SELECT * FROM {ifc_class} WHERE ifc_id = ?`, `__setattr__` does a live `UPDATE` + `commit()` (this backend is read/write, unlike `stream`). `GeometryCache`/`GeometryCacheShape`/`GeometryCacheGeometry` TypedDicts document the expected verts/edges/faces/material_ids/materials binary layout.

Dependencies: `sqlite3` (stdlib, optional import), `numpy`/`numpy.typing`, `json`. **Filesystem- and native-sqlite3-module-dependent** — but conceptually the closest analog to what a browser target might want: a pre-baked, queryable, columnar-ish IFC dataset for fast partial loading. In-browser this shape maps naturally onto `sql.js`/WASM SQLite, or IndexedDB with a similar table layout — worth flagging as a plausible "large model" strategy for IfcOpenShell-TS, distinct from the primary in-memory WASM `file` object.

### 2.10 `ifcopenshell/draw.py` (737 lines, skimmed per task scope)

Purpose: 2D drawing/SVG generation and serialization pipeline (floorplans, elevations, sections) built **on top of** `ifcopenshell.geom` (the real geometry API — see §4 below) plus `shapely` for 2D polygon algebra and `xml.dom.minidom` for SVG post-processing. `draw_settings` is a large dataclass of SVG/HLR (hidden-line-removal) knobs mirroring `ifcopenshell.geom.settings` SVG-prefixed keys. `main(settings, files, iterators=(), merge_projection=True, progress_function=..., logger=None)` is the entry point, orchestrating iterators, `ARRANGE_POLYGON_SETTINGS` (native `arrange_polygon_settings`), and geometry serializers.

This module is a downstream consumer of the geometry API rather than part of the core file/entity binding — relevant to IfcOpenShell-TS only insofar as it confirms `ifcopenshell.geom` (not `ifcopenshell.geom.app`) is the real, non-GUI geometry API (see §4), and that `shapely`-equivalent 2D polygon math would be a separate JS dependency if 2D drawing generation is ever ported.

## 3. Low-level binding surface (`ifcopenshell_wrapper` — the layer a TS/embind binding must replicate)

Source: `src/ifcopenshell-python/ifcopenshell/ifcopenshell_wrapper.pyi` (1695 lines; the *generated* `ifcopenshell_wrapper.py`/`_ifcopenshell_wrapper.so` are build artifacts, not checked into source — this `.pyi` is the hand-maintained type-stub description of that generated surface).

### 3.1 Core parsing/data classes

## 4. Geometry access API (real API, distinct from the GUI)

Per task scope: `ifcopenshell.geom` (`src/ifcopenshell-python/ifcopenshell/geom/`) contains **five** files, not one monolithic module:

- **`__init__.py`** (57 lines) — just detects optional `pythonocc` (`OCC.Core`) availability (`has_occ`), conditionally imports `occ_utils`, and does `from .main import *`.
- **`main.py`** (772 lines) — **this is the real, non-GUI geometry API**, confirmed by its imports (`ifcopenshell_wrapper`, no Qt). It is the module actually re-exported as `ifcopenshell.geom.*`.
- **`app.py`** (682 lines) — confirmed Qt GUI: `from PyQt5 import QtCore, QtGui, QtWidgets`, plus `multiprocessing`, imports `.main` and `.code_editor_pane`/`.occ_utils` for an interactive geometry-debugging desktop tool. **Out of scope for TS — no GUI to port.**
- **`code_editor_pane.py`** — Qt code-editor widget, part of the GUI. Out of scope.
- **`occ_utils.py`** (310 lines) — pythonOCC (desktop OpenCASCADE Python bindings) interop helpers, only loaded `if has_occ`. Desktop-only (native OpenCASCADE build), not applicable to a WASM/browser target — the WASM build presumably ships one of the non-OCC kernels (CGAL/manifold, per `GEOMETRY_LIBRARY` below) or a WASM-compiled OpenCASCADE without the Python-specific glue.

### `geom/main.py` — the real API surface

- **`settings(settings_mixin, ifcopenshell_wrapper.settings)`** — a Pythonic wrapper (`settings_mixin`) over the native key/value settings object. `set(k, v)` / `get(k)` normalize dashed/underscored setting names (`"iterator-output"` ↔ `ITERATOR_OUTPUT`), delegate to native `set_`/`get_`, with one Python-only synthetic setting `use-python-opencascade` (desktop-only). `setting_names()`, `build_parser(argparse.ArgumentParser)`/`apply_namespace()` (CLI plumbing — out of scope for TS but shows the setting-name→type mapping: `bool`, `int`, `double`, `std::string`, `std::set<int>`, `std::set<std::string>`, `std::vector<double>`, plus three enum types `IteratorOutputOptions`/`FunctionStepMethod`/`OutputDimensionalityTypes`/`TriangulationMethod`). The full `SETTING` literal union (§ in main.py lines 64-167) enumerates ~80 named settings (angle-unit, apply-default-materials, circle-segments, context-ids/types/identifiers/priorities, dimensionality, iterator-output, length-unit, precision, triangulation-type, use-world-coords, weld-vertices, y-up, plus ~30 SVG-drawing-specific ones consumed by `draw.py`) — **this is the config surface an embind `settings` object needs to expose 1:1** (as get/set by string key, or as a typed options object in TS).
- **`GEOMETRY_LIBRARY = Literal["cgal", "cgal-simple", "manifold", "opencascade", "hybrid-cgal-simple-opencascade"]`** and `has_geometry_library(name) -> bool` — geometry kernel selection is a **runtime string parameter**, not a compile-time choice from Python's perspective; a given native build may or may not have all kernels compiled in. Relevant for WASM: only whichever kernel(s) are compiled into the WASM build will report `True`.
- **`iterator(ifcopenshell_wrapper.iterator)`** — the main bulk-geometry-processing entry point. Constructor: `(settings, file_or_filename, num_threads=1, include=None, exclude=None, geometry_library="opencascade", logger=None)`. Accepts either an already-open `file` or a path (opens it itself). `include`/`exclude` accept either `entity_instance` lists (routed to `construct_iterator_with_include_exclude_id`, converted to STEP ids first) or class-name string lists (routed to `construct_iterator_with_include_exclude`). Iteration protocol: `initialize() -> bool`, then loop `get()` (current shape element) / `next() -> bool` / `progress() -> int (0-100)`; `__iter__` wraps this as a Python generator. `get_task_products()` for parallel-processing task introspection. **`num_threads` — native multithreading**, presumably backed by real OS threads or a thread pool in the C++ core; a WASM build would need this mapped either to Web Workers + SharedArrayBuffer (requires cross-origin-isolation headers) or forced to `num_threads=1` — **flag this explicitly as a browser-compat blocker/design decision**, not a simple API translation.
- **`consume_iterator(it, with_progress=False)`** / **`iterate(settings, file_or_filename, num_threads=1, include=None, exclude=None, *, with_progress=False, geometry_library="opencascade", logger=None)`** — generator sugar over `iterator`.
- **`create_shape(settings, inst, repr=None, geometry_library="opencascade", logger=None)`** — the single-element (non-bulk) geometry entry point; polymorphic return depending on `inst`'s type (`IfcProduct` → element-with-geometry; `IfcRepresentation`/`IfcRepresentationItem`/`IfcProfileDef` → raw shape; `IfcPlacement`/`IfcObjectPlacement` → `transformation`; `IfcTypeProduct` → `None` or error). Delegates to `ifcopenshell_wrapper.create_shape`.
- **`map_shape(settings, inst) -> item`** — maps IFC geometry to the internal taxonomy representation (schema-agnostic), e.g. `IfcCartesianPoint` → a `point3` with `.components`.
- **`tree(ifcopenshell_wrapper.tree)`** — spatial index / clash-detection API: `add_file(file, settings)`, `add_iterator(iterator)`, `select(value, completely_within=False, extend=...)` (point/box/entity spatial query → `list[entity_instance]`), `select_box(...)`, `clash_intersection_many`/`clash_collision_many`/`clash_clearance_many(set_a, set_b, tolerance/allow_touching/clearance, check_all)` → `tuple[clash,...]`, `get_clash_type(i) -> "protrusion"|"pierce"|"collision"|"clearance"`. A meaningful chunk of API for a web viewer wanting clash detection / ray-picking.
- **`serializers`** (metaclass-driven attribute factory) — `serializers.obj/svg/ttl/gltf/glb/collada/dae/stp/step/igs/iges/usd/usda/usdc(out_filename, settings)` → `ifcopenshell_wrapper.create_geometry_serializer(...)`, i.e. **file-format exporters that write geometry to disk** (or to an in-memory `ifcopenshell_wrapper.buffer` for the "stream serializers" subset `{"obj","svg","ttl"}`). `serializers.guess_from_extension(filepath)`. **Filesystem-write-oriented by default** — the `buffer` in-memory escape hatch (§ below) is the interesting part for a browser port.
- **`ifcopenshell_wrapper.buffer`** (from the `.pyi`, §3): `__init__(*args)`, `filename()`, `get_value()`, `is_ready()` — an in-memory sink alternative to a real file path for streaming-capable serializers (`obj`/`svg`/`ttl`). This is the cleanest existing precedent in the codebase for "give me bytes back instead of writing a file," and should be the model for how IfcOpenShell-TS's geometry-serialization API returns data to JS (typed arrays) instead of writing to a virtual FS path.

### The actual triangulated-mesh data shape (from the `.pyi`, §3.1 already covered but repeated here for the geometry section's sake)

`ifcopenshell_wrapper.triangulation` (a `representation` subtype, obtained via `create_shape(...).geometry` when `settings.set("iterator-output", TRIANGULATED)`, the default) exposes, as both tuple-typed and raw-bytes-typed properties (buffer variants are clearly meant for zero-copy bulk transfer — **the `*_buffer` properties are exactly the shape a WASM→JS `Float32Array`/`Int32Array`/`Uint8Array` view should target**):
- `verts` / `verts_buffer` (flat float xyz), `normals`/`normals_buffer`, `uvs`, `colors_buffer`
- `faces` / `faces_buffer` / `faces_tri` (triangle vertex-index triples), `edges`/`edges_buffer`, `edges_item_ids`/`edges_item_ids_buffer`
- `item_ids`/`item_ids_buffer`, `material_ids`/`material_ids_buffer`, `materials -> tuple[style,...]`
- `polyhedral_faces_with_holes`/`polyhedral_faces_without_holes` (non-triangulated alternative output, `settings` `triangulation-type` = `POLYHEDRON_WITH_HOLES`/`POLYHEDRON_WITHOUT_HOLES` vs default `TRIANGLE_MESH`)

Alternative representation modes controlled by `settings.set("iterator-output", ...)`: `TRIANGULATED` (default, → `triangulation`/`triangulation_element`), `NATIVE` (→ `native`/`native_element`, raw kernel B-rep, e.g. for CAD-grade export), `SERIALIZED` (→ `serialization`/`serialized_element`, has `brep_data`, `surface_style_ids`, `surface_styles` — a portable serialized-brep string, used by the `use-python-opencascade` bridge). For a mesh-focused web viewer, `TRIANGULATED` is almost certainly the only mode worth binding in v1.

`element`/`triangulation_element`/`native_element`/`serialized_element` (the per-product wrapper the `iterator`/`create_shape` return): `id`, `guid`, `name`, `type`, `parent_id`, `context`, `product -> entity_instance`, `transformation`/`transformation_buffer`, `unique_id`, and `.geometry` (the `triangulation`/`native`/`serialization` payload above).

## 5. SWIG interface findings (`src/ifcwrap/IfcParseWrapper.i`, `src/ifcwrap/IfcPython.i`)

What the SWIG layer does, concretely, to turn C++ `ifcopenshell::file` / `express::base` into the Python surface documented above — each of these is a decision an embind layer needs to make explicitly:

1. **Renaming** (`%rename`) — C++ method names differ from their Python-exposed names: `instance_by_id`→`by_id`, `instance_by_guid`→`by_guid`, `instances_by_type`→`_by_type`, `instances_by_type_excl_subtypes`→`_by_type_excl_subtypes`, `get_inverse`→`get_inverses_by_declaration` (freeing up `get_inverse` for the Python-side higher-level meaning), `express::base`→`entity_instance`, `add_entity`→`_add`, `remove_entity`→`_remove`, `traverse`→`_traverse`, `traverse_breadth_first`→`_traverse_breadth_first`. **The underscore-prefixed names are the "raw primitive, Python-mixin wraps it" convention** flagged in §1/§2.2 — an embind API should keep this same split (expose the raw primitives under matching names, let a TS mixin provide the friendly names).

2. **Custom constructor via `%feature("shadow")`** — `file.__init__(self, schema=None, schema_identifier=None, schema_version=None)` is hand-written Python replacing the raw multi-overload C++ ctor, calling a shared `_determine_schema_identifier` static helper (duplicated between `file.py`'s `file_mixin._determine_schema_identifier` and this shadow code — worth having `file_mixin`'s version be the single source of truth in the TS port, with the WASM ctor accepting only a resolved schema identifier string).

3. **`%extend` blocks add C++ methods that don't exist on the underlying class**, purpose-built for the Python binding — these are exactly the "glue" behaviors an embind layer must reimplement natively rather than expect for free:
   - `file::file_pointer()` — `reinterpret_cast<size_t>($self)`, i.e. the C++ pointer value exposed as an integer, used for identity comparisons (`file.__eq__`/`__hash__`) and as the `file_mixin.post_init` registry key. **A WASM/embind port needs an equivalent stable identity handle** — in Emscripten this is usually the object's underlying pointer (`getPointer()`in embind, or a ref-counted opaque numeric handle), and it needs equally careful handling since embind, like SWIG, mints new JS wrapper objects on each accessor call unless caching is added.
   - `file::create_uninitialized()` / two-phase `initialize()` for the `bypass_types` streaming-skip use case.
   - `file::_get_inverse` / `_get_inverse_indices` / `get_total_inverses` — thin dispatchers requiring the argument to be `express::entity` (throw `ifcopenshell::exception` otherwise).
   - `file::_write(fn)` → `helper_fn_atomic_write` — **atomic write via temp-file + rename** (issue #4797: interrupted writes must never corrupt the destination). This specific guarantee doesn't transfer meaningfully to a browser (no destination file to protect against interruption when you're handing back an in-memory buffer/Blob) but documents an intentional correctness property of the reference implementation worth preserving conceptually (e.g. don't yield a partially-serialized buffer on error).
   - `file::create(name, id=-1)`, `entity_names()`, `types()`, `schema_identifier()`, `storage_mode()` (0=in-memory,1=rocksdb,-1=other), `key_value_store_iter`/`key_value_store_query` (RocksDB-only, `#ifdef IFOPSH_WITH_ROCKSDB`).
   - `file.__eq__`/`__ne__`/`__hash__` (Python-side, via `%pythoncode`) built on `file_pointer()`.
   - **The `this` setattr hook**: `%pythoncode { def __setattr__(self, k, v): object.__setattr__(self, k, v); if k == 'this': self.post_init(int(v)) }` — this is *the* mechanism wiring a freshly-constructed native object into `file_mixin`'s identity-keyed state registry (§2.2). **This confirms the exact trigger point** a TS port needs to replicate: right after a new WASM `file` object's underlying handle is known, the TS mixin layer must be initialized/registered by that handle's identity.
   - `express::base::get_attribute_category(name) -> 0|1|2|3` — the C++ implementation behind `entity_instance.get_attribute_category`, scanning `all_attributes()` (checking `derived()[i]` for category 3) then `all_inverse_attributes()`. Straightforward linear scan over schema metadata; an embind layer can either replicate this scan in C++ (as here) or push it up to a TS-side cached lookup table per entity-type (likely faster in practice, avoiding a JS↔WASM call on every attribute access — worth considering for the TS design, especially given `entity_instance_mixin.__getattr__`/`__setattr__` call this on **every single attribute access**).
   - `express::base::__len__`, `get_attribute_names()`, `get_inverse_attribute_names()`, `is_a(str)`/`is_a(bool)`, `get_argument(i|name)`, `__hash__` (via `identity()`), `__repr__`/`to_string(valid_spf=true)`, `file_pointer()` (owning-file identity, 0 if none), `get_argument_index(name)`.
   - **`set_attribute_value_py(i, PyObject* value)` — the single most detailed, load-bearing piece of glue in the whole file.** It re-derives the attribute's `argument_type` (via `helper_fn_attribute_type`, itself dispatching on whether the declaration `as_entity()`/`as_type_declaration()`/`as_enumeration_type()`, and consulting `derived()[i]`) and then does a big `switch` over the ~15-way `ifcopenshell::argument_type` enum, each branch converting the incoming Python value with hand-written, permissive coercions: `PyNumber_Index` for ints (accepts numpy ints/bools too), `PyFloat_AsDouble` for doubles (accepts int-likes), `PyUnicode`/`PyBytes` for strings, tribool logic for `LOGICAL` (`True`/`False`/`"UNKNOWN"`/`0`/`1`/`-1`/`2`), enum-name string lookup for `ENUMERATION` (via `enum_type->lookup_enum_offset`), binary-string validation for `BINARY` (`ifcopenshell::valid_binary_string` + `boost::dynamic_bitset`), `PySequence_Fast` + per-element coercion for every aggregate variant (`AGGREGATE_OF_INT/DOUBLE/STRING/BINARY/ENTITY_INSTANCE`, and 2-level-nested `AGGREGATE_OF_AGGREGATE_OF_INT/DOUBLE/ENTITY_INSTANCE`), and a `to_base` helper using raw `SWIG_ConvertPtr`/`SWIG_TypeQuery` to unwrap a Python `entity_instance` back to a C++ `express::base` value (const and non-const pointer attempts). **This is the definitive, exhaustive spec of "how do I take a JS value the user set on an attribute and turn it into the correctly-typed underlying representation" — an embind `set_attribute_value` needs to reproduce this exact type-dispatch table**, including its permissiveness (accepting numpy-int-like objects, bytes-or-str for strings, int 0/1/-1/2 for tribool logical) and its `None`→`blank{}` short-circuit (setting to `None` in Python always means "unset," bypassing the type switch entirely, regardless of whether the attribute is optional).
   - `spf_header::file_description_py/file_name_py/file_schema_py` — upcasting getters exposed as Python `@property`s, because the base `spf_header` C++ methods return a type SWIG can't introspect further without help.
   - Free functions `open(fn, readonly=false, logger=nullptr)` / `read(data)` / `stream_from_string(data)` — note `open`/`read` wrap the actual parse in `Py_BEGIN_ALLOW_THREADS`/`Py_END_ALLOW_THREADS` (release the GIL during the C++ parse so other Python threads can run) — **a real-threading concern with no WASM equivalent** (no GIL, and no threads at all unless the WASM build specifically uses pthreads+SharedArrayBuffer); flag as "drop, no-op, or map to Worker-based async" in the TS design rather than attempt a literal translation.
   - Named-type/simple-type/aggregation-type/type-declaration/select-type/enumeration-type/attribute/inverse-attribute/entity/schema-definition `%pythoncode` blocks add only `__repr__` implementations — cosmetic, safe to skip or trivially replicate as `toString()`.
   - `get_info_cpp` / `convert_cpp_attribute_to_python` — the C++ implementation of the fast recursive `get_info()` path (§2.3), built as a `attribute_value` (`std::variant`-like) visitor producing nested Python dicts directly in C++, avoiding a Python-level per-attribute recursive walk. Confirms this bulk-serialize-to-plain-object pattern is a deliberate, hand-optimized fast path worth replicating identically in the embind layer (return a fully-built JS object/Map in one call).
   - `instance_streamer::read_instance_py` — similarly a big hand-written visitor producing a Python dict per streamed instance directly in C++ (id/type + all forward attributes, with a special two-key `{"type":...,"value":...}` shape for simple/defined-type wrapped values and a `{"ref": id}` shape for not-yet-resolved forward references during streaming) — mirrors the shape `stream2`/`stream2_from_string` (in `__init__.py`) hand to Python callers.
   - `logger::__iter__` (iterates `log_messages()`), `log_message::severity_string`/`to_dict`/`to_tuple`/`__eq__`/`__hash__`/`__repr__`.

4. **`%ignore` list** — mostly internal/non-Python-relevant C++ members (`register_inverse`, `build_inverses*`, `byguid_`/`byid_`/`byref_excl_` raw storage maps, `begin`/`end`/`types_begin`/`types_end` C++ iterators replaced by the `%extend`-provided vector-returning methods above, `operator<`/`operator==`/`operator!=` on `express::base` because SWIG's naive translation crashes on `None`/isn't needed since the Python mixin defines safe equivalents, `in_memory_file_storage`/`rocks_db_file_storage` internal storage variant types). Useful mainly as "these C++ internals don't need embind equivalents at all."

5. **`%exception` global wrapper** (`IfcPython.i`) — every wrapped call is try/caught for `attribute_out_of_range_exception` → Python `IndexError`, generic `ifcopenshell::exception`/`std::runtime_error` → `RuntimeError`, anything else → generic `RuntimeError("An unknown error occurred")`. **An embind layer needs an equivalent blanket exception-translation boundary** (C++ exceptions → JS `Error` subclasses, e.g. mapping `attribute_out_of_range_exception` to a JS `RangeError`), since by default Emscripten either aborts or throws an opaque pointer-typed exception, not a catchable, informative JS `Error`.

6. **`std_vector.i`/`std_string.i`/`std_shared_ptr.i`/`std_unique_ptr.i`/`stdint.i` includes + a `std::array<double,3>` template instantiation (`DoubleArray3`)** — standard SWIG library typemaps that make `std::vector<T>`↔Python-tuple, `std::string`↔Python-str, and smart-pointer ownership work automatically. In embind, the closest equivalents are `embind`'s built-in `std::vector`/`std::string` bindings (via `register_vector`/native string marshaling) plus manual ownership-annotation (`allow_raw_pointers`, `nonnull`, etc.) — none of this is exotic for embind, but the **the size of `typemaps_in.i`/`typemaps_out.i`/`type_conversion.i` (902 lines combined)** doing custom per-type Python conversions (see `attribute_value` visitor pattern in `typemaps_out.i`, driven by a tagged-union/`std::variant`-shaped C++ type) signals that IFC's attribute-value representation is itself a tagged union in C++ (`ifcopenshell::attribute_value`, wrapping `blank`/`derived`/`bool`/`tribool`/`int64_t`/`double`/`std::string`/`enumeration_reference`/`express::base`/`empty_aggregate`/`empty_aggregate_of_aggregate`/`std::vector<...>` nested up to 2 levels, `boost::dynamic_bitset` for binary) — **the embind binding's single highest-value piece of design work is this attribute-value marshaling boundary**, both directions (`get_argument`/`attribute_value` out, `set_attribute_value_py` in), matching §5.3's `set_attribute_value_py` switch and the `typemaps_out.i` `attribute_value` visitor.

7. **`register_schema` / `schema_by_name` / `declaration_by_name` return upcast pointers** (`%typemap(out) ifcopenshell::declaration* / parameter_type*` in `typemaps_out.i`, checking `as_named_type()`/`as_simple_type()`/`as_aggregation_type()` etc. and constructing the appropriately-SWIG-typed Python object) — i.e. **polymorphic C++ class hierarchies are down-cast to their most specific type at the Python boundary automatically**. An embind layer needs the same behavior (embind supports polymorphic class downcasting via `class_<Derived, base<Base>>` registration + `wrapper` return-type dispatch, but it must be set up explicitly per hierarchy — `declaration`→`entity`/`type_declaration`/`enumeration_type`/`select_type`, and `parameter_type`→`named_type`/`simple_type`/`aggregation_type`).

## 6. Express codegen role (`ifcopenshell/express/`, skimmed per task scope)

`src/ifcopenshell-python/ifcopenshell/express/` (`__init__.py`, `bootstrap.py`, `codegen.py`, `definitions.py`, `express_parser.py`, `nodes.py`, `mapping.py`, `rule_compiler.py`, `rule_executor.py`, `schema.py`, `schema_class.py`, plus `header_schema.exp`/`express.bnf`, and `rules/` per-schema generated rule modules) is a **standalone, runtime tool, not a build-time codegen step for the built-in schemas.** The compiled-in IFC2X3/IFC4/IFC4X3 schema definitions live in the C++ core (compiled from `.exp` separately at the native build level, outside this Python package). This Python `express` subpackage exists for two runtime purposes: (1) parsing arbitrary/custom `.exp` EXPRESS schema files into a `schema_class.SchemaClass` object that can be registered at runtime via `ifcopenshell.register_schema()` (§2.1), letting users define and load non-standard IFC-like schemas without recompiling the C++ core; and (2) compiling a schema's EXPRESS derivation/global rules (`WHERE` clauses, derived-attribute formulas) into executable Python functions (`rule_compiler.py`/`rule_executor.py`, consumed by `entity_instance_mixin.__getattr__`'s derived-attribute fallback in §2.3, and by `validate.py`'s `express_rules=True` path) — this is genuinely a small Python-embedded compiler (its own `.bnf` grammar + parser), not something to port line-by-line; for IfcOpenShell-TS, the equivalent need (custom schema support, derived-attribute/rule evaluation) is a distinct, lower-priority feature to design fresh in TS rather than transliterate.

## 7. Browser/WASM compatibility notes (summary)

Concrete blockers/adaptations, gathered from the sections above:

| Concern | Where it shows up | Notes |
|---|---|---|
| **Filesystem path I/O** | `ifcopenshell.open()` (Path.exists, native `open(path)`), `file_mixin.write()` (Path.mkdir, native `_write(fn)`), `template.create` is fine (in-memory), `convert_path_to_rocksdb` | Core `file.open`/`file.write` need a browser-native surface: accept `ArrayBuffer`/`Uint8Array`/`Blob`/`File` in, return `Uint8Array`/`Blob` out, instead of paths. Emscripten's virtual FS (MEMFS) can shim this but a purpose-built binary-in/binary-out API is cleaner than pretending there's a filesystem. |
| **Zip handling** | `.ifcZIP` open path (`zipfile` + `tempfile.TemporaryDirectory`) | Needs a JS zip library (e.g. `fflate`) plus in-memory extraction, no temp directory. |
| **RocksDB backend** | `rocksdb_lazy_instance`/`rocksdb_file_storage` (`file.py`), `RocksDbSerializer`/`RocksDBPrefixIterator`, `file.storage`/`storage_mode()`/`key_value_store_*`, `convert_path_to_rocksdb` | Entirely native-filesystem-backed embedded DB (`IFOPSH_WITH_ROCKSDB` build flag), directory-based. Not portable to WASM without a WASM RocksDB build (uncommon) or dropping the feature entirely for v1 — likely **out of scope** for IfcOpenShell-TS; the `sqlite`-backend precedent (§2.9, mapping cleanly onto `sql.js`/IndexedDB) is a more realistic "large model" strategy if one is needed. |
| **`sqlite3` backend** | `sql.py`'s `class sqlite(file)` | Needs stdlib `sqlite3` (native). Would need `sql.js` (WASM SQLite) or an IndexedDB-based reimplementation with the same table shape (`metadata`, `id_map`, per-class attribute tables, `shape`/`geometry` tables for baked meshes) to carry the same idea into the browser. |
| **`stream.py` file-seek backend** | `class stream(file)` | Assumes a real seekable file handle kept open (`self.file.seek(offset)`), plus optional `lark` grammar parsing. In-browser, an equivalent would need to work against an in-memory buffer or `Blob.slice()`, and the underlying rationale (avoid loading huge files fully into desktop RAM) is weaker when the file is already a `File`/`ArrayBuffer` in browser memory to begin with — likely a **lower-priority feature**; the full in-memory WASM `file.open` path is probably sufficient for v1. |
| **Native multithreading** | `ifcopenshell.geom.iterator(..., num_threads=N)`, `Py_BEGIN_ALLOW_THREADS`/`Py_END_ALLOW_THREADS` around `open`/`read` in `IfcParseWrapper.i` | No GIL-release equivalent needed in JS (single-threaded by default), but real multi-threaded geometry processing in WASM requires pthreads + `SharedArrayBuffer`, which requires the page to be served with `Cross-Origin-Opener-Policy`/`Cross-Origin-Embedder-Policy` headers (COOP/COEP) — a hosting/deployment constraint, not just a code-porting one. Decide early whether IfcOpenShell-TS v1 targets `num_threads=1` only, or commits to the COOP/COEP requirement. |
| **Plugin search paths** | `set_plugin_search_paths`/`get_plugin_search_paths`/`clear_plugin_search_paths` (native `.so`/`.dll` discovery for geometry-kernel/schema plugins) | Native dynamic-library loading concept; meaningless in WASM (no dynamic linking of native code from JS at runtime in the same sense) — likely a no-op/removed API in TS, with kernel selection instead being a WASM-build-time choice (§4, `GEOMETRY_LIBRARY`). |
| **Subprocess-based derived-rule compilation** | `entity_instance_mixin.__getattr__`'s EXPRESS derived-attribute fallback (`subprocess.run([sys.executable, "-m", "ifcopenshell.express.rule_compiler", ...])`), and more broadly the `express/` package's use of `importlib`, `os.listdir(".")`, `subprocess` | Not part of the base file/entity API's hot path (only triggered for `calc_*` derived-attribute lookups on custom/uncommon schemas) but is fundamentally desktop-process-model-shaped. Out of scope for a v1 port; would need a from-scratch design (e.g. pre-bundling rule modules, or a JS-side EXPRESS rule interpreter) if ever prioritized. |
| **CLI/argparse tooling** | `validate.py`'s `__main__` block, `settings.build_parser`/`apply_namespace` | Not relevant to a library API; skip, or repurpose only the underlying logger/statement shape (`json_logger`) for a browser UI. |
| **`numpy`/binary blob geometry unpacking** | `sql.py`'s `get_geometry()` (`np.frombuffer`) | Conceptually maps cleanly to `Float64Array`/`Int32Array` views over an `ArrayBuffer` in JS — not a blocker, just confirms the intended binary layout (`verts`: f64, `edges`/`faces`/`material_ids`: i32) that a TS geometry API should also expose as typed-array views rather than JS number arrays, for the same performance reasons the C++/Python boundary already cares about (see the `triangulation` `*_buffer` properties in §4). |
| **GIL / object identity quirks** | `file_mixin.registry` keyed by `int(self.this)` (native pointer identity), `post_init` hook on `this` assignment | Not GIL-specific, but the "new wrapper object minted per Python attribute access, must be reconciled via pointer identity" pattern (§1, §2.2, §5 point 3) is a SWIG artifact that **embind may or may not share** — needs verification during binding design; if embind object identity/caching behaves differently (e.g. if `embind::class_` can be configured to always return the same JS object for the same C++ pointer), the TS port might be able to *avoid* needing this registry-by-pointer-identity workaround altogether, simplifying `file_mixin`/`entity_instance_mixin` relative to their Python originals. |
| **Random UUID / crypto** | `guid.new()` (`uuid.uuid4()`) | Trivial: use `crypto.randomUUID()` (available in all modern browsers and Node ≥14.17) or a small RNG-based UUIDv4 polyfill. Not a real blocker, listed only for completeness. |
