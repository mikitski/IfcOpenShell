# Research 06 — `wrappergen` N-API Validation Spike: Results

Status: spike results, resolving `10-architecture.md` §3's gated decision and
`30-open-questions.md` §A item 1's "timeboxed validation spike" condition. Written against
`v0.9.0` commit `899919305`, on branch `ts/phase-1-wrappergen-spike`.

**Verdict: PASS.** Extend `wrappergen` for Phase 1's real primitive binding rather than
hand-writing `node-addon-api` glue. The generator's core design (clang discovery, the C-ABI/
N-API-extension/TS-facade emitter split, the handle/enum/sequence adapter system) held up at
full real-header-set scale and under a genuinely new "variant" adapter kind added for this
spike. A real, compiled, linked `.node` addon — generated by the extended tool, not
hand-written — opens an IFC4 file from an in-memory buffer, creates an `IfcWall` entity, reads
its declaration, and gets/sets its `GlobalId` attribute through the new variant adapter,
verified by actually running it under Node, not just by compiling it. Getting there required
five real, non-trivial fixes to the generator (detailed in §3) and surfaced one confirmed
runtime memory-safety bug that needed a new handle-kind concept to fix correctly (§3.5) — this
is not a clean, no-surprises pass, and the write-up below is deliberately specific about
exactly what had to change and why, per this spike's explicit "a well-argued FAIL is just as
valuable as a PASS" mandate.

## 1. Scope actually covered

Per `10-architecture.md` §3's fallback-condition wording: add the variant adapter, buffer-based
file open, and a minimal N-API binding for `file` + `entity_instance` (`express::base`) +
`declaration`, enough to open a file, create/read/write one entity's attributes, and query its
declaration.

Concretely, delivered:

1. **Variant adapter** (`conventions.py`, `model.py`, `emit.py`) — a new, third adapter kind
   (`variant:<cpp-type>`) alongside the existing `handle:`/`enum:`/`sequence:` kinds, config-
   declared rather than clang-discovered (§2.1 explains why), threaded through the C-API,
   N-API, and TS-facade emitters.
2. **Buffer-based file open** — `ifcopenshell::file(void* data, int data_size, ...)`
   (`file.h`, already existed in the C++ core) is now reachable via a new `"buffer"` parameter
   adapter mapped from `void*` (`type_adapters={"void*": "buffer"}`), needing **zero** new
   emitter code beyond the existing scalar-adapter machinery.
3. **`get_info_cpp` equivalent — partially, with the gap documented.** `attribute_count()`/
   `attribute_by_index()`/`attribute::name()` are already discoverable, real, correct
   primitives a TS-side loop can use to enumerate an instance's attributes one at a time. A
   genuine single-call bulk serializer (a sequence-of-variant return) was **not** implemented —
   see §4's "what's still missing" for exactly what that needs and why it was descoped.
4. **`emit_napi_extension`** (`emit.py`) — structurally parallel to `emit_python_extension`:
   same per-class/per-callable walk over the same `ModuleModel`/`_all_variants(model)`,
   `napi_get_cb_info`/`napi_create_external`/`napi_get_value_external` replacing
   `PyArg_ParseTuple`/`PyCapsule_*`.
5. **`emit_typescript_facade`** (`emit.py`) — structurally parallel to `emit_python_facade`:
   same per-`ClassModel`/`CallableModel` walk, a TS class with a private handle field replacing
   Python's `__slots__` class, emitting `.d.ts`-friendly signatures directly.
6. **`src/wrappergen/napi_spike.py`** — the narrowed `WrapperConfig` + the two injected
   `free_function`-kind `CallableModel`s (`get_attribute_value_variant`/
   `set_attribute_value_variant`, from the new shim) that produce the actual generated output
   in `src/wrappergen/napi_spike_generated/` (checked in as a snapshot, same convention as the
   existing `generated/` directory).
7. **`src/wrappergen/shim/attribute_value_shim.h`/`.cpp`** — hand-written C++ (not code-
   generated; see §2.1) playing the same role `IfcParseWrapper.i`'s `set_attribute_value_py`/
   `convert_cpp_attribute_to_python` play for SWIG: the one place the ~15-way dispatch
   actually has to be written by hand, regardless of which binding technology is chosen.
8. **A real, compiled, linked, and *run* `.node` addon** proving the above — see §5.

## 2. The variant adapter — design and why it's config-declared, not discovered

### 2.1 Why `ifcopenshell::attribute_value` can't be clang-discovered as the variant

`research/04` §1.2 predicted the fix would be "emit a small tagged-union C struct... and one
shared conversion helper." That's what got built, but the path there needed one more finding
first: `express::base::get_attribute_value(size_t) const` already returns
`ifcopenshell::attribute_value` (`instance_data.h`) — a real class, already clang-discoverable
as an ordinary `handle:` target. The reason this isn't already "the variant adapter" is that
`ifcopenshell::attribute_value`'s entire read API is **C++ implicit-conversion operators**
(`operator int64_t()`, `operator bool()`, `operator std::string()`, ... `operator
express::base()`, up to `operator std::vector<std::vector<express::base>>()`) — `clang_frontend.py`'s
`_discover_methods` only walks `CursorKind.CXX_METHOD` cursors, and a conversion operator is a
distinct cursor kind (`CONVERSION_FUNCTION`) that was never in scope. Even if it were
discovered, there's no single method to point an adapter at — the *caller* has to already know
which conversion to invoke, which for `ifcopenshell::attribute_value` is `raw.type()` (an
`ifcopenshell::argument_type`, matching the callable dispatch key
`IfcParseWrapper.i`'s `set_attribute_value_py` computes by hand for Python, per
`research/01-python-core-and-lowlevel.md` §5 point 6).

This confirms `research/04`'s framing exactly: the real gap isn't clang's discovery pipeline —
it's that there is no generic, introspectable "this C++ value is one-of-N cases" shape in the
real code for the generator to walk. A hand-written shim supplying that shape is not a
workaround unique to the generated-binding path; it is what any binding technology needs
here, generated or hand-written (SWIG's `.i` typemaps are exactly this, done by hand,
one language at a time).

### 2.2 The shim (`src/wrappergen/shim/attribute_value_shim.h`/`.cpp`)

```cpp
class IFC_PARSE_API attribute_value_variant {
  public:
    attribute_value_kind kind = ATTRIBUTE_VALUE_KIND_NULL;
    int64_t integer_value = 0;
    double double_value = 0.0;
    int logical_value = 2; // 0 = false, 1 = true, 2 = unknown
    std::string string_value;
    express::base entity_value;
};

attribute_value_variant get_attribute_value_variant(const express::base& instance, int attribute_index);
void set_attribute_value_variant(express::base& instance, int attribute_index, const attribute_value_variant& value);
```

`get_attribute_value_variant` calls the real `express::base::get_attribute_value()`, reads its
`.type()`, and switches on it to pick the matching conversion operator. `set_attribute_value_variant`
switches on `value.kind` and calls the correctly-typed `express::base::set_attribute_value`
overload — these are explicitly instantiated in `parse.cpp` for every scalar and aggregate case
(`template void IFC_PARSE_API express::base::set_attribute_value<int64_t>(...)`, etc.), so the
shim only needs the *declaration* visible, not the definition, exactly like calling any other
exported `IFC_PARSE_API` function.

**Covered, verified working end to end (§5): `BOOL`, `LOGICAL`, `INTEGER`, `DOUBLE`, `STRING`,
`ENUMERATION`, `ENTITY_INSTANCE`.** Deliberately **not** implemented: `BINARY` and the five
`AGGREGATE_OF_*`/`AGGREGATE_OF_AGGREGATE_OF_*` cases — `research/01` §5's other ~7 branches of
the real ~15-way dispatch. This is a genuine, disclosed scope cut (not a wall this spike hit
and couldn't get past): each remaining case is the same *mechanism* (a new
`attribute_value_kind` + a new `VariantCaseModel` entry + a shim branch), not a new kind of
problem, and is real, scoped follow-up work for Phase 1 proper, not spike scope.

### 2.3 Generator-side design: a config-declared adapter + two injected `CallableModel`s

`ModuleModel` gained `VariantAdapterModel`/`VariantCaseModel` (`model.py`) — the one adapter
kind in the whole system that is **not** discovered from a clang cursor, but supplied directly
by the tool author (`napi_spike.py`'s `_attribute_value_variant_model()`), the same way
`class_owner_types`/`class_handle_kinds` already are. `emit.py` threads it through:

- `_return_c_type`/`_parameter_c_type` — resolve to the emitted C struct's name.
- `emit_c_api_header` — emits the `ifcopenshell_attribute_value_kind_t` enum and
  `ifcopenshell_attribute_value_variant_t` struct (POD, `extern "C"`-safe: `int64_t`/`double`/
  `char*`/opaque-handle-pointer fields only — confirmed the "no Python/JS type leaks into the C
  ABI" property `research/04` verified for the existing adapters still holds for this one).
- `emit_c_api_implementation` — `_emit_variant_parameter_conversion`/`_emit_variant_return_lines`
  convert between the C++ shim type and the C struct, field-by-field, driven by the
  `VariantCaseModel` list (no hand-generated dispatch code per case — genuinely data-driven).
- `emit_napi_extension` — the GET direction returns a **plain JS value** of the correct type
  (number/boolean/string/wrapped-entity-handle/`null`) matching Python's `get_argument`
  ergonomics exactly (§2.4 below is the one place this spike *didn't* fully match that
  ergonomic bar). The SET direction reads a small tagged JS object (`{kind, ...}` mirroring the
  C struct) — see §2.4.

The two real accessor functions (`get_attribute_value_variant`/`set_attribute_value_variant`)
are **not** clang-discovered either — they're free functions taking the instance explicitly as
their first argument (not real C++ methods of `express::base`), so `_discover_methods`
wouldn't find them even with the earlier CONVERSION_FUNCTION gap closed. `napi_spike.py`
injects them directly as `CallableModel`s with a new `kind="free_function"`, handled by four
small, targeted additions to `emit.py` (`_call_expression`'s self-expression branch, and
broadening three `"method"` kind checks to `{"method", "free_function"}`) — a bounded, clean
extension of the existing pipeline, not a parallel one.

### 2.4 A disclosed ergonomic gap: SET takes a structured value, not a bare polymorphic one

Python's `set_attribute_value_py` accepts a bare, dynamically-typed value (`wall.Name = "x"`)
and re-derives the attribute's `argument_type` from schema metadata itself to disambiguate
(e.g. a Python `int` vs. `float` vs. an enum-name `str` vs. a plain `str`, all before ever
looking at the JS/Python value). This spike's `set_attribute_value_variant`'s N-API wrapper
instead expects the caller to supply the kind explicitly (`{kind: native.STRING, string_value:
"x"}`), rather than inferring it from a bare JS value's `typeof`. This is a deliberate,
disclosed scope cut, not an oversight: JS's `typeof` cannot disambiguate `INTEGER` vs. `DOUBLE`
(one JS `number` type) or `STRING` vs. `ENUMERATION` (one JS `string` type) without first
knowing the attribute's *declared* type — exactly the schema lookup Python's binding does by
hand. The concrete fix for a non-spike Phase 1: add a small `attribute_kind_of(instance, index)`
free function to the shim (trivial — it's exactly `get_attribute_value_variant`'s existing
`type()`-lookup, without the value-conversion switch) and expose it as an **ordinary enum-return
method** — no new adapter machinery needed, since `attribute_value_kind` can be modeled as a
plain `enum:` target — then have the TS mixin layer (Phase 2, not Phase 1's primitive layer)
call it before converting a bare `wall.Name = "x"` assignment into the structured call. This is
real, understood, bounded follow-up work, not an open question.

## 3. Generator fixes this spike needed — the "does it hold up at full scale" evidence

All five of these are real bugs/gaps in `wrappergen` as it existed before this spike, found by
actually pointing it at the real, full `src/ifcparse/*.h` header set (not just `file.h`+
`express.h`) and by actually compiling and running the output, not just generating it.

### 3.1 Parameters couldn't resolve to handle types (`clang_frontend.py`)

`_resolve_return_adapter` already tried a handle-adapter match when a return type didn't match
a scalar/enum; `_resolve_parameter_adapter` never did the equivalent for *parameters*. Any
constructor or method with **any** class-handle-typed parameter — including an optional,
trailing one, e.g. every `ifcopenshell::file` constructor's `ifcopenshell::logger& logger =
ifcopenshell::logger::root()` — was silently dropped in full: `_build_parameter_models` returns
`None` for the whole callable the moment one parameter fails to resolve. This is exactly why
the checked-in `generated/` snapshot has zero handle-typed parameters anywhere and only
ever exposes `file`'s path-based constructors (never `add_entity`, never `set_attribute_value`,
never the buffer constructor once its trailing `logger&` is accounted for). Fixed by extending
`_resolve_parameter_adapter` to also attempt a handle-adapter match, mirroring the return-side
logic exactly. Real, general, and required to expose the primitives Phase 1 actually needs
(`file::add_entity`, `express::base::set_attribute_value(index, express::base&)`, etc.) —
the buffer-based file-open constructor's optional trailing `logger&` parameter would not have
compiled through to a usable variant at all without this fix.

### 3.2 The same gap in "which classes get selected" (`clang_frontend.py`)

Fixing 3.1 surfaced a second, related bug: `build_module_model`'s `used_class_names` collection
only scanned `callable_model.return_adapter` for `handle:`/`sequence:` targets, never
`parameter.adapter`. A class referenced only through a parameter (never a return type) could
now *resolve* correctly but never make it into `selected_classes`, producing a `KeyError` in
`emit.py` the first time such a parameter was emitted. Fixed by scanning parameters the same
way returns already were.

### 3.3 Silent wrong-type inference on missing system headers (`clang_frontend.py`)

`_build_translation_unit`'s no-`compile_commands.json` fallback path (the one
`generate.py --repo-root ... --output-dir ...`'s default config always uses) passes only
project-specific `-I` flags to `clang.cindex.Index.parse` — it never adds the toolchain's
default system/standard-library search paths the way invoking the `clang` driver executable
directly does. Without them, `#include <string>` (etc.) fails with a fatal diagnostic, and
clang's C++ error-recovery silently reinterprets the now-unresolved `std::string` as `int` —
**with no exception raised**, so the tool "succeeds" and emits plausible-looking but wrong
bindings (`declaration::name() -> integer` was observed, where the real signature returns
`const std::string&`). This is worse than a coverage gap: it's a silent-corruption risk with no
built-in way to notice it happened. Fixed two ways: (a) `_check_diagnostics` now raises loudly
on any clang ERROR/FATAL diagnostic for a parsed header, turning "silently wrong" into "loudly
broken" as a hard backstop; (b) `_default_system_include_args()` best-effort auto-discovers
`clang++ -print-resource-dir` (portable) and, on macOS, `xcrun --show-sdk-path` +
`-isystem<sdk>/usr/include/c++/v1` (matching what the driver injects automatically), used only
when no `compile_commands.json` is configured. **(b) is a portability improvement, not a
guarantee** — a Linux box with a correctly configured system clang wouldn't have hit this at
all (this is why the checked-in `generated/` snapshot's `char*`-typed string returns are
already correct — it was almost certainly generated via a working `compile_commands.json` or a
correctly-configured environment); (a) is the actually load-bearing fix, and is a small,
unconditional, high-value addition regardless of platform.

### 3.4 A real, pre-existing `ifcparse` header-hygiene bug, surfaced (not fixed) by (a) above

Turning on loud diagnostics immediately caught a second, independent, genuinely pre-existing
issue in `src/ifcparse/rocksdb_map_adapter.h`: it uses `std::vector`/`std::string`/
`std::ostringstream` as ordinary member/parameter types without including `<vector>`/
`<string>`/`<sstream>` itself, relying on an *includer* having already pulled those in first —
true when `IFOPSH_WITH_ROCKSDB` is defined (real RocksDB headers happen to pull in enough
of the C++ standard library transitively) and false otherwise. On strict, hermetic-per-header
libc++ (this sandbox), the file fails to parse standalone at all without `IFOPSH_WITH_ROCKSDB`
defined and real RocksDB headers on the include path; on the more permissive libstdc++
(commonly the default on Linux, where the checked-in snapshot's generation environment almost
certainly ran), it likely goes unnoticed. **This is a real bug in `ifcparse` itself, out of
scope for this PR** (only `src/wrappergen/`, the new shim, and this research doc are in scope —
see the task's explicit "don't touch `src/ifcparse/`, `src/ifcwrap/`" boundary). Worked around
for this spike two ways: `generate.py`'s default header discovery now excludes
`rocksdb_map_adapter.h`/`rocksdb_set_view.h` by name (both are RocksDB-storage-backend-only,
already explicitly out of scope for the whole IfcOpenShell-TS project per `research/01`'s
compatibility table); and `napi_spike.py`'s clang args force-`-include vector -include string
-include sstream` ahead of any real header, a standard, narrowly-scoped workaround for exactly
this class of missing-transitive-include bug. **Recommend filing this as its own small, focused
follow-up fix to `src/ifcparse/rocksdb_map_adapter.h`** (add the three missing includes) — it's
a one-line-per-include fix, unrelated to wrappergen, and worth landing independently of this
PR's scope.

### 3.5 A confirmed runtime memory-safety bug: "value" handle_kind assumes safe-to-copy

The most serious finding, and the one requiring genuine new generator design work, not just a
bug fix. `wrappergen`'s existing "value" handle_kind assumes a class returned by pointer/
reference is safe to dereference-and-copy into the wrapper struct (`_emit_handle_return_lines`:
`auto result = *result_ptr;` then `new {c_type}{ std::move(result) }`). This **compiles cleanly**
against `ifcopenshell::schema_definition`, `ifcopenshell::declaration`, `ifcopenshell::attribute`,
`ifcopenshell::entity`, `ifcopenshell::type_declaration`, and `ifcopenshell::aggregation_type` —
none of them has a deleted copy constructor. It is nonetheless a **real double-free /
use-after-free**: `schema_definition::~schema_definition()` (and several of the others'
destructors) `delete`s every pointer it holds, on the assumption that it is the unique owner —
true for the actual, single, process-wide singleton instance (`Ifc4::get_schema()`'s
function-local `static std::unique_ptr<schema_definition>`), false for a copy manufactured by
this exact "value" handle_kind emission path. Confirmed by an actual reproducible crash during
this spike's own verification (not a static analysis finding): calling `file.schema()` through
the generated binding, then `declaration_by_name()` on the *result*, corrupted enough state that
subsequent lookups returned wrong data (an empty declaration name for a lookup that should have
succeeded) and the process later segfaulted on exit. A standalone, non-generated C++ reproduction
(`diag.cpp`, not part of this PR) confirmed the mechanism precisely: copying `*file.schema()`
into a local `schema_definition` and letting the copy go out of scope crashes; using the real
pointer directly does not.

**Fix: a new, third `handle_kind`, `"borrowed"`.** A `"borrowed"` class's wrapper stores the raw
pointer directly (`{cpp_name}* value;`, non-const to accommodate the real API's inconsistent
const-qualification across constructors vs. accessors) — no dereference, no copy, no delete
(`_free`'s generic `delete handle;` only destroys the wrapper struct; a raw pointer member has
no destructor of its own to run). Threaded through: `_emit_handle_return_lines` (pointer and
reference returns both handled — a reference return takes its address), `_cpp_argument`
(parameter unwrapping), `_call_expression` (method-call syntax), the per-class struct
definition, and — since the same unsafe-copy pattern existed in the **sequence**-return path
too (`schema_definition::declarations()`, `entity::all_attributes()`, etc. all return
`std::vector<const T*>`) — `_emit_sequence_return_lines` and the generated list's `_get`
accessor, both fixed the same way (`std::vector<T*>`, pointers copied not dereferenced).
Applied to the whole schema-introspection class family
(`declaration`/`type_declaration`/`select_type`/`enumeration_type`/`entity`/`attribute`/
`inverse_attribute`/`schema_definition`/`parameter_type`/`named_type`/`simple_type`/
`aggregation_type`) via `class_handle_kinds` in `napi_spike.py`.

**This is the single most important finding of the spike relative to the fallback condition's
own wording** — `10-architecture.md` §3 explicitly asks whether `class_owner_types`' model
holds up, and the concrete answer is: **not fully**. The existing model has exactly two shapes
(owned-by-another-class-with-shared_ptr-tied-lifetime, or an independent value type safe to
copy) and no representation for a third, common real shape — a long-lived, singleton/registry-
owned object reached only by pointer, that must never be copied or deleted through the wrapper.
`"borrowed"` is that third shape, and it is now a real, working, generator-level concept, not a
workaround bolted on outside the model.

### 3.6 A silent, no-crash correctness bug found only by actually running the round-trip

Two bugs, both found only by executing the generated code under Node (not by compiling it, and
not by static review):

- **A dangling `std::string::c_str()`.** `emit_napi_extension`'s SET-direction variant-parameter
  conversion originally wrote `js_value.string_value = const_cast<char*>(napi_string_value(env,
  prop).c_str())` — `napi_string_value` returns a `std::string` **by value**; its `.c_str()`
  pointer dangles the instant that temporary is destroyed, before the native call downstream
  ever reads it. Silent, no compiler warning, no crash observed in this specific test run
  (classic dangling-pointer UB: sometimes the freed stack slot still looks valid). Fixed by
  hoisting a named `std::string` local (function-scope lifetime) to own the backing storage.
- **`NULL`-kind fell through to a generic integer branch.** The GET-direction variant-return
  switch (`emit_napi_extension`) built its per-case dispatch generically off each
  `VariantCaseModel`'s `field_kind`, and `NULL`'s case (`field_kind="integer"`, reusing
  `integer_value`) matched the same "else: `napi_create_int64`" branch as `BOOL`/`INTEGER` —
  producing a JS **number** `0` for an unset attribute instead of `null`. Fixed by having the
  `NULL` case fall through to the `default:` branch (`napi_get_null`) instead of emitting an
  explicit `case`.

Both are exactly the class of bug the roadmap's Phase 1 exit criterion anticipated needing
ASAN/UBSan CI and real integration tests to catch (`20-roadmap.md` Phase 1: "a native memory bug
here doesn't throw catchably like a JS exception... this is the one bug class a passing TS test
suite structurally cannot catch") — confirmed accurate by this spike hitting exactly that shape
of bug twice, and only catching it by actually running the code end to end.

## 4. What's still missing / explicitly out of scope

- **Full ~15-way variant dispatch.** `BINARY` and the five `AGGREGATE_OF_*` cases (§2.2).
- **Bulk `get_info_cpp` single-call serializer.** Only per-attribute enumeration primitives
  (`attribute_count`/`attribute_by_index`/`attribute::name`) were verified; a genuine
  sequence-of-variant bulk call needs the variant adapter extended to interoperate with the
  sequence adapter (a `std::vector<attribute_value_variant>` case), not yet built.
- **SET-direction ergonomics** (§2.4) — structured `{kind, ...}` input rather than a bare
  polymorphic value; the fix is understood and small (an `attribute_kind_of` enum-return
  method, reusing existing adapter machinery) but not implemented in this spike.
- **CMake integration.** No `src/wrappergen/CMakeLists.txt` target builds
  `napi_spike_generated/`'s output or links a `.node` file — see §5 for why (no Node headers/
  cmake-js infrastructure available in this sandbox to validate a CMake target against; wiring
  this in is real, but separate, follow-up work for Phase 1 proper, once it's building the full
  primitive surface, not just this spike's narrow slice).
- **`emit_python_extension`/`emit_python_facade` do not support the variant/buffer/`borrowed`
  additions.** Not needed — this spike's model is a separate, narrower `WrapperConfig`
  (`napi_spike.py`) that never invokes the Python emitters, so the existing `generated/`
  snapshot and its Python facade are completely untouched by this PR.

## 5. Verification — what actually ran, and what couldn't run locally

**What ran, for real, in this sandbox:**

1. `src/wrappergen/napi_spike.py` executed against the **real** `src/ifcparse/` header set (all
   27 headers, minus the two RocksDB-storage ones per §3.4) using `clang.cindex` bound to
   Apple's system `libclang.dylib` (no network access to PyPI in this sandbox for the official
   `libclang`/`clang` packages — the pure-Python `clang.cindex`/`clang.enumerations` modules were
   fetched directly from `llvm/llvm-project` on GitHub instead, one of the few external hosts
   reachable from this sandbox; this is a local-verification detail, not something shipped).
   Produced `src/wrappergen/napi_spike_generated/`'s four files (31 classes discovered and
   selected).
2. The generated C API implementation and N-API extension were compiled with the system
   `clang++` against the **real** `src/ifcparse` headers, **real** Node.js N-API headers
   (`/usr/local/include/node`, bundled with this sandbox's Node 20 install), and Boost 1.86
   headers (fetched from `boostorg/boost`'s GitHub release, since no system Boost was present)
   — both compile cleanly with **zero errors**.
3. `src/ifcparse`'s core `.cpp` files, `src/plugin/plugin.cpp`, and the IFC4 schema
   (`schemas/Ifc4.cpp`/`Ifc4-schema.cpp`/`Header_section_schema*.cpp`) were compiled directly
   with `clang++` (no CMake — not available in this sandbox; this mirrors the "no local C++
   build toolchain" limitation Phase 0's agent already hit and worked around via CI, per
   `PROGRESS.md`). A small, spike-only bootstrap (`plugin::module::builtin(...)` +
   `schema_registry_instance().bind(...)`, not part of this PR's shipped code) statically
   registers the IFC4 schema in-process instead of using the normal filesystem-plugin-discovery
   path, since no plugin search directory exists in this sandbox.
4. Everything was linked into a real `.node` file (`clang++ -bundle -undefined dynamic_lookup`,
   the standard macOS technique for a Node native addon build without linking against a Node
   import library) and **actually run under Node 20** via `node
   src/wrappergen/napi_spike_generated/verify_spike.js <path-to-.node>` — see that file for the
   exact, checked-in test. All checks pass (§0's summary).

**What could not be verified locally, and why:** the actual Phase 1 build (a real `node-gyp`/
`cmake-js`-driven build wired into `src/ifcopenshell-ts/`, or a CMake target under
`src/wrappergen/`) needs a full CMake + Boost + toolchain environment this sandbox doesn't have
